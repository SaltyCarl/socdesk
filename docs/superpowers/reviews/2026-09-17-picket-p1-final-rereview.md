## New findings

### Important

**N1. Ubuntu 24.04 de-socketing is incomplete, and the script's own check cannot see it** (`tools/picket/install.sh:60-70`; partial of I5).
- Ubuntu's documented revert to a non-socket-activated sshd is: `systemctl disable --now ssh.socket` → `rm -f /etc/systemd/system/ssh.service.d/00-socket.conf` → `rm -f /etc/systemd/system/ssh.socket.d/addresses.conf` → `systemctl daemon-reload` → `systemctl enable --now ssh.service`. The script performs only the first and last (plus a restart). `00-socket.conf` is the drop-in that binds `ssh.service` to `ssh.socket`; left in place, `enable --now ssh.service` pulls the socket back in and sshd inherits the `:22` listener, so the drop-in's `Port 2222` is ignored on this target.
- `sshd -T` (`:70`) reports the *configuration*, so it prints `port 2222` even while the daemon is listening on `:22` via the socket — the "EFFECTIVE sshd config" banner is misleading here. The `ssh -p 2222` pause is the only thing that catches it, and the README's recovery advice (§3:111-114, "fix `00-picket.conf`") does not address the cause.
- Severity is bounded by the pause (no lock-out; `:22` keeps serving the open session and new ones) — but the script cannot complete step 2 correctly on one of its two documented targets, and the operator is left without a documented way forward.
- **Fix (4 lines):** between `systemctl disable --now ssh.socket` and `systemctl enable --now ssh.service` add `rm -f /etc/systemd/system/ssh.service.d/00-socket.conf /etc/systemd/system/ssh.socket.d/addresses.conf` and `systemctl daemon-reload`. Add to the printed check `ss -ltnp | grep -E 'sshd' || true` so the operator sees the **listening** port, not just the configured one, and mirror that in README §3's expected output and recovery text ("on Ubuntu confirm `systemctl is-active ssh.socket` is `inactive`"). Alternatively, narrow README §2 to Debian 12 as the only supported target until an Ubuntu dogfood proves the branch.

### Minor

**N2. `GIT_TERMINAL_PROMPT=0` does not reach git through `sudo`** (`install.sh:148`). `VAR=x sudo -Hu picket git …` sets the variable in sudo's environment; the default `env_reset` strips it for the child, so git never sees it. Consequence: on a missing/private repo the (interactive) run prompts for credentials instead of failing fast — not a strand. Fix: `sudo -Hu picket env GIT_TERMINAL_PROMPT=0 git clone -q …`.

**N3. Compose image pinning is implicit** (`install.sh:101`; pre-existing, noticed while re-reading step 4 — not introduced by the wave). `docker-compose.host.yml` declares both `image: ghcr.io/djkurlander/knock-knock:latest` and `build: .`; on a fresh box Compose builds from the pinned `v3.0.0` checkout, but any path that pulls the image (`docker compose pull`, a non-fresh host with a cached `:latest`) would run `:latest` code while the exporter reads the `v3.0.0` registry. Dogfood check: `docker compose images` shows a locally built image; consider `docker compose up -d --build` (or `docker compose build && docker compose up -d`) to make the pin explicit.

**N4. Screenshots predate the chip change** — documented in PICKET.md §9 (`tab-*.png` show *Live* where the live app now ages the fixture to *Silent*). Re-shoot at dogfood with real data; nothing to fix now.

No new Critical. No regression found in the pipeline, collector, schemas or web tiers: the walker keeps every schema bound, `additionalProperties:false` is intact on every object (report's scripted walk; my read agrees), no fabricated values were introduced, and the hostile fixture still validates so the second pass is what acts.
