# IOC-reporting: storage architecture assessment

**Date:** 2026-08-20
**Scope:** which Cloudflare-native (or external) store backs the IOC-reporting /
moderation-queue / abuse-leaderboard feature, and how approved data reaches
the public lookup card. Single dimension of a larger design; this file does
not cover UI, auth-provider selection in depth, or the OSINT-feed ingestion
side.

## Current architecture (grounding)

SOCDesk today is deliberately storeless: Vite/React static site on Cloudflare
Pages, a handful of Pages Functions under `functions/api/*.js` (e.g.
`functions/api/enrich.js`), and committed JSON datasets regenerated by a
GitHub Actions pipeline (`docs/superpowers/specs/2026-07-28-socdesk-cti-platform-design.md`,
§3). The one existing Function (`/api/enrich`) is same-origin, stateless, and
uses Cloudflare's default edge `caches.default` — no KV namespace, no DB
binding. Non-goals at v1 explicitly excluded "authentication, user accounts,
or server-side per-user state" — the reporting feature is the first thing to
cross that line, so the store choice sets precedent.

## 1. Store choice

**Recommendation: Cloudflare D1.**

| Store | Free tier (current, verified against Cloudflare docs) | Fit |
|---|---|---|
| **D1** (SQLite, GA since 2024-04-01) | 5,000,000 rows read/day, 100,000 rows written/day, 5 GB storage/account (500 MB/database, 10 databases), resets daily 00:00 UTC. Free-plan Time Travel PITR to any minute in the last 7 days at no cost, always-on, no setup. | **Best fit.** Relational + SQL aggregation is exactly what "dedup reports by IOC, compute a proposed reputation, roll up by ASN" needs — `GROUP BY ioc_value`, `COUNT(DISTINCT reporter_account_id)`, join to `accounts`. Binds to Pages Functions with a plain `wrangler.toml` D1 binding — same deploy shape as the existing `functions/api/*.js` convention, zero new infra paradigm. |
| **KV** | 100,000 reads/day, 1,000 writes/1,000 deletes/1,000 list-ops per day, 1 GB storage, eventually consistent (up to ~60s global propagation). | **Wrong shape.** No query/aggregation — dedup-by-IOC and ASN rollups would require hand-maintained counter keys, which is exactly the class of bug-prone denormalization D1 avoids for free. The 1,000 writes/day cap is also the tightest of any option here: a single report (insert report + touch an aggregate + touch a rate-limit counter) can burn 2-3 writes, so KV's write ceiling bites first, not last. Eventual consistency is also wrong for an owner reviewing a queue and expecting to see their own approvals immediately. |
| **Durable Objects** (SQLite-backed, only backend on free plan) | 100,000 requests/day, 13,000 GB-s/day duration. | **Right consistency model, wrong tool class.** DO's free-tier SQLite storage is capable enough, but DOs are built for single-writer stateful coordination (a queue *actor*, a rate limiter, a websocket room) — not a multi-table relational schema with ad hoc rollup queries. It also doesn't bind to Pages Functions as directly: DO classes need to live in a Worker, adding a second deploy artifact next to Pages. D1 gets the same durability story with less new machinery. |
| **External (Supabase/Turso/Neon)** | Comparable or larger free tiers (Turso: 5 GB, 500M rows read/mo, 100 DBs; Supabase: 500 MB Postgres + 50K auth MAU; Neon: 0.5 GB/project, 100 CU-hrs/mo). | **Ruled out primarily on the stated weighting.** Task explicitly says weigh "stays on the Cloudflare platform" heavily — an external store adds a second account, a second secret to rotate, cross-service network latency on every write, and no capability D1 lacks at this volume. Keep as a documented fallback only if D1's free tier is ever provably insufficient (see §4 — it isn't, even at 100x). |

D1 free-tier headroom for LOW/portfolio volume: comfortable by 2-3 orders of
magnitude (see §4). D1 is GA (April 2024), not beta — this is a mature,
supported product, not an early-access risk.

**Accounts / auth note** (in scope since `accounts` is one of the four
tables asked about): two Cloudflare-native options exist for "signed-in
analysts" —
- **Cloudflare Access** (Zero Trust): free for up to 50 authenticated users,
  zero code, sits in front of a route. Free cap makes it a poor fit for the
  *public* reporting surface (an unbounded, LinkedIn-shared audience could
  hit 50 users), but it is a very good fit for the **owner-only moderation
  admin surface**, where "one person" is permanently under the cap.
- **GitHub OAuth** (or similar, verified in a Pages Function, session in a
  signed cookie), rows in a D1 `accounts` table: unbounded, zero-cost,
  idiomatic for a public dev-tool audience of security analysts who already
  have GitHub accounts. Recommended for the analyst-facing report-submission
  flow; Access reserved for the admin/moderation surface.

## 2. Data model

All four tables live in one D1 database (well under the 500 MB free
per-database cap even at 100x projected volume).

```sql
-- Signed-in analysts who can submit reports.
CREATE TABLE accounts (
  id              INTEGER PRIMARY KEY,
  provider        TEXT NOT NULL,          -- 'github'
  provider_sub    TEXT NOT NULL,          -- provider's stable user id
  handle          TEXT NOT NULL,
  created_at      TEXT NOT NULL,
  role            TEXT NOT NULL DEFAULT 'analyst',  -- 'analyst' | 'owner'
  status          TEXT NOT NULL DEFAULT 'active',   -- 'active' | 'banned'
  UNIQUE (provider, provider_sub)
);

-- Raw submissions. Never read by the public site.
CREATE TABLE reports (
  id                INTEGER PRIMARY KEY,
  ioc_value         TEXT NOT NULL,
  ioc_type          TEXT NOT NULL,        -- 'ipv4' | 'domain'
  category          TEXT NOT NULL,        -- 'c2' | 'phishing' | 'brute-force' | ...
  comment           TEXT,
  evidence_url      TEXT,
  reporter_id       INTEGER NOT NULL REFERENCES accounts(id),
  reported_at       TEXT NOT NULL,
  status            TEXT NOT NULL DEFAULT 'pending',  -- 'pending'|'approved'|'rejected'
  reviewed_by       INTEGER REFERENCES accounts(id),
  reviewed_at       TEXT,
  review_note       TEXT
);
CREATE INDEX idx_reports_queue ON reports (status, reported_at);
CREATE INDEX idx_reports_ioc   ON reports (ioc_value, status);
CREATE INDEX idx_reports_rate  ON reports (reporter_id, reported_at); -- abuse/rate-limit checks

-- Materialized rollup of APPROVED reports only. This is the table the
-- publish step reads from.
CREATE TABLE ioc_reputation (
  ioc_value               TEXT PRIMARY KEY,
  ioc_type                TEXT NOT NULL,
  approved_report_count   INTEGER NOT NULL,
  distinct_reporters      INTEGER NOT NULL,
  category_breakdown_json TEXT NOT NULL,   -- {"c2":3,"phishing":1}
  asn                     INTEGER,
  asn_org                 TEXT,
  first_reported_at       TEXT NOT NULL,
  last_reported_at        TEXT NOT NULL,
  last_published_at       TEXT
);

-- Optional: pre-aggregated for the leaderboard so publish is a flat SELECT
-- instead of a GROUP BY over the full table at every export.
CREATE TABLE asn_leaderboard (
  asn                  INTEGER PRIMARY KEY,
  asn_org              TEXT,
  distinct_iocs        INTEGER NOT NULL,
  approved_report_count INTEGER NOT NULL,
  updated_at           TEXT NOT NULL
);
```

**Read/write paths:**

- **Submit** — `POST /api/reports` (new Pages Function, D1-bound): verify
  session, rate-limit by `reporter_id`, validate IOC shape/category, `INSERT
  INTO reports`. Write-only touch of D1.
- **Moderate** — an owner-only admin surface (behind Cloudflare Access):
  `SELECT ... WHERE status='pending' ORDER BY reported_at`, then on
  approve/reject, `UPDATE reports SET status=...`, and on approve,
  recompute the affected row(s) of `ioc_reputation` (and touch
  `asn_leaderboard`) inside the same transaction. Read+write, admin-gated.
- **Publish** — a scheduled/triggered export step reads `ioc_reputation` +
  `asn_leaderboard` (approved data only) and writes committed JSON. This is
  the question in §2 worth designing deliberately:

### Serve path: regenerate the committed dataset vs. live-query from `/api/enrich`

**Recommendation: regenerate the committed client-side dataset. Do not
live-query D1 from the read path.**

Reasoning:
- **Matches the existing model exactly.** SOCDesk already treats "the
  dataset behind a lookup card" as something a pipeline regenerates and
  commits — the CVE catalog and IOC repository work this way today. Adding
  `ioc_reputation.json` / `asn_leaderboard.json` as more pipeline outputs is
  zero new architecture, just a new source feeding the same commit-and-deploy
  path (reuse the GitHub Actions workflow: an export step runs after an
  approval batch, e.g. via `wrangler d1 execute --command` or a small
  admin-authenticated export endpoint, and commits alongside the other
  collector outputs).
- **Matches the product's own cadence.** The spec is explicit that the owner
  "reviews batches on a schedule" — there is no requirement for
  approval-to-live-card latency of zero. A publish step (triggered right
  after an approval batch, or on the existing collector cron) is a feature
  fit, not a compromise.
- **Directly delivers §3** (read path stays store-free) — see below.
- **Caps the blast radius of a schema mistake or a D1 outage** to the
  write/admin side only; the public site never notices.

Trade-off accepted: a freshness lag between "owner clicks approve" and "the
lookup card shows it," bounded by publish cadence (make it same-day/on-demand
if desired — trivial to trigger the export synchronously after an approval
batch rather than waiting for the next cron tick). Worth a small UI note
("reputation reflects the last published batch") so the lag reads as
intentional, not broken.

**Rejected alternative:** live-querying D1 from `/api/enrich` at read time
would remove that lag, but couples the anonymous hot path to D1's
availability and read quota, adds a network hop of latency to every
lookup, and is a real architectural change (every visitor becomes a D1
reader) for a freshness improvement the product doesn't ask for. Also
directly weakens §3's guarantee.

## 3. Read-path cleanliness

**Confirmed achievable, with the regenerate-dataset design.** D1 is touched
by exactly three surfaces: the report-submission Function (write), the
owner-only moderation admin Function(s) (read+write, Access-gated), and the
publish/export step (read, feeding committed JSON — same trust boundary as
the existing collector pipeline, not the browser). The lookup/analyzer card
continues to fetch the same kind of static, committed JSON it does today;
`/api/enrich` and the client bundle gain no new dependency on D1, no new
binding, no new failure mode. This holds *only* under the regenerate-dataset
choice above — a live-query design would violate it by construction.

One caveat that is not a storage concern but is a genuinely new attack
surface: `/api/reports` is a new **authenticated write** endpoint that
didn't exist before. It needs the standard protections (session
verification, per-account rate limit, input validation on `comment`/
`evidence_url`) — orthogonal to the store choice, but worth flagging since
it's the actual new exposure this feature introduces.

## 4. Scale + failure modes

- **100x volume.** LOW/portfolio volume today is plausibly dozens–low
  hundreds of reports/month. 100x is still low thousands/month. A report
  write is ~2-3 D1 row-writes (insert `reports` row, touch `ioc_reputation`,
  touch `asn_leaderboard`); even 1,000 reports/day × 3 writes = 3,000/day —
  3% of the 100,000/day free write cap. Moderation-queue browsing and
  leaderboard reads are trivially inside 5,000,000/day. **The real
  100x-scale strain point is not D1 — it's the single-owner review
  process.** "One person reviews batches on a schedule" doesn't scale with
  report volume; that bottleneck shows up long before any Cloudflare quota
  does. The more realistic threat at scale is **submission-endpoint abuse**
  (bot/spam reports inflating the queue) rather than legitimate volume —
  mitigate with Turnstile (free, Cloudflare-native) + per-account rate
  limiting at write time, not at the store layer.
- **Free-tier cliffs.** D1's daily write cap (100,000/day) is a hard wall
  once hit (`D1_ERROR` on further writes until UTC reset), but is nowhere
  near this workload even at 100x. Storage (500 MB/database, 5 GB/account)
  is a non-issue for text reports — tens of thousands of rows are low
  single-digit MB. The tier that *would* have cliffed early is KV's
  1,000 writes/day, reinforcing why it's ruled out in §1.
- **Backup / data-loss posture.** D1 Time Travel gives free, automatic,
  always-on point-in-time recovery to any minute in the last 7 days (free
  plan) with zero setup — no cron, no manual snapshot step. Combined with
  the regenerate-dataset design, the *published* reputation data is doubly
  protected (git history of the committed JSON + D1 Time Travel on the
  source-of-truth tables). For extra margin at low cost, a periodic
  `wrangler d1 export` to R2 (10 GB free) alongside the existing pipeline
  would be belt-and-suspenders, but isn't required to clear a reasonable
  bar at this volume.
- **Migration cost if this choice is wrong later.** D1 speaks standard
  SQLite; `wrangler d1 export` produces a portable SQL dump (to
  Turso/libSQL, self-hosted SQLite, or as a base for a Postgres migration).
  Because the read path never touches D1 directly (regenerate-dataset
  model), a future store swap would only touch the write/admin/publish
  Functions — the public site and its deploy path are completely
  insulated. This is the strongest argument for the regenerate-dataset
  choice independent of the store pick: it makes the store an
  implementation detail, not a public commitment.

## 5. Top risks + recommendation

**Risk 1 — submission-endpoint abuse**, not storage capacity, is the
realistic threat model: bot/spam reports poisoning the moderation queue and
burning the owner's review time. Mitigate at the write path (Turnstile,
auth, per-account rate limits), not the store.

**Risk 2 — single-owner moderation bottleneck.** The data model and D1
handle arbitrary volume comfortably; the "one person reviews batches on a
schedule" process is the actual scaling constraint if report volume ever
became non-trivial.

**Recommendation:** Cloudflare **D1** for the store — native to the
platform, binds to Pages Functions with no new deploy paradigm, and its
relational/SQL model is the right shape for dedup-by-IOC and ASN rollups
that KV and Durable Objects would force into awkward hand-rolled counters.
Serve approved data by **regenerating the committed client-side dataset**
(reusing the existing collector-pipeline pattern) rather than live-querying
D1 from `/api/enrich` — this keeps the public lookup path exactly as
store-free as it is today and confines the new write surface to the
report-submission and admin-moderation Functions only.
